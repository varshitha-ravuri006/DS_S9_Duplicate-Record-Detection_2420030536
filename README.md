# Duplicate Record Detection System

A data science project that finds records describing the same person even when
they are written differently, and then measures how well it does that.

```
Record A                      Record B
Name:  Ravi Kumar             Name:  Ravi K
Email: ravi.kumar@gmail.com   Email: ravikumar@gmail.com
Phone: 9876543210             Phone: +91-9876543210
City:  Hyderabad              City:  HYD
```

No field is identical, but this is almost certainly one person.

---

## Problem Statement

Customer databases collect the same person more than once. Someone fills a form
twice, one entry comes from a web signup and another from a call centre, or the
same person is typed in with a spelling mistake. The records then differ in ways
that carry no meaning - capital letters, spacing, `+91`, `Rd` instead of `Road`,
`HYD` instead of `Hyderabad`.

`df.drop_duplicates()` only removes rows that are identical character for
character. On this dataset that catches **13 of 108** real duplicate pairs -
about 12%. The rest need something better.

The problem is also harder than it first looks in the other direction: two
different people can share a name, a city and even an address. A system that
only looks at names will confidently merge two siblings.

## Objective

1. Detect exact duplicates, formatting differences, capitalisation differences,
   spelling mistakes, abbreviations and near-duplicates.
2. Handle missing values without treating a blank as agreement.
3. Do it without comparing every record with every other record.
4. **Measure the result** with precision, recall, F1 and a confusion matrix
   against a known ground truth.

Point 4 is the one that matters. It is the difference between "I found some
duplicates" and "I know how often my method is right, and I know how it fails."

## Dataset

Generated by [`data/make_dataset.py`](data/make_dataset.py) rather than
downloaded, because evaluation needs labels and a real customer database does
not come with a list of its own duplicates.

| | |
|---|---|
| Records | 445 |
| Columns | 7 (`record_id, name, email, phone, address, city, pincode`) |
| Blank cells | 53 |
| Exact duplicate rows | 13 |
| True duplicate pairs | 108 |
| Labelled "confusable" pairs | 70 |

The generator creates a set of distinct people, then adds messy copies of some
of them:

```
name     Ravi Kumar / RAVI KUMAR / ravi kumar / Ravi K / Mr. Ravi Kumar / Rvai Kumar
phone    9876543210 / +91 9876543210 / +91-98765-43210 / 09876543210 / 98765 43210
address  12 MG Road Hyderabad / 12, M.G. Road, Hyderabad / 12 MG Rd Hyderabad
city     Hyderabad / HYD / hyderabad / Hyd
```

Two design choices in the generator matter more than the variations:

**Confusable records.** 70 pairs are *different people* who look alike - the
same name in the same city, and sometimes the same address (siblings). Without
these, every similar-looking pair would be a true duplicate and the evaluation
would be meaninglessly easy.

**Identifier drift.** Roughly 20% of duplicate copies have their phone changed
or blanked, and 20% have their email changed or blanked. An earlier version of
the generator did not do this, and the result was a dataset where every
duplicate kept a perfectly matching phone and email - one exact rule solved the
whole problem and the F1 score was a meaningless 1.00.

`entity_id` is used internally to build `ground_truth.csv` and is then dropped.
The detector never sees it.

### 1. Inspection ([`src/preprocessing.py`](src/preprocessing.py))

Shape, dtypes, missing values, unique values, exact duplicates. Read the CSV
with `dtype=str`: phone and pincode are identifiers made of digits, and letting
pandas treat them as numbers would drop leading zeros.

The most useful output is the uniqueness ratio, because it is where the scoring
weights come from:

| column | unique | ratio | reading |
|---|---|---|---|
| email | 379 | 0.85 | identifier-like - a match is strong evidence |
| phone | 395 | 0.89 | identifier-like - a match is strong evidence |
| city | 28 | 0.06 | categorical - a match is weak evidence |

### 2. Normalization

Each raw column keeps its original values and gains a `_norm` twin.

| | before | after |
|---|---|---|
| name | `"  Mr. RAVI   Kumar "` | `ravi kumar` |
| email | `" RAVI@GMAIL.COM "` | `ravi@gmail.com` |
| phone | `"+91-98765-43210"` | `9876543210` |
| address | `"12, M.G. Road"` | `12 mg road` |
| city | `"HYD"` | `hyderabad` |

Measured effect:

```
 column   unique_before  unique_after  reduction
   name            365           329       9.9%
  phone            395           362       8.4%
address            388           340      12.4%
   city             28             7      75.0%
pincode             47            47       0.0%
```

City is the headline: 28 spellings collapse to 7 real cities. Pincode does not
move at all, which honestly means those rules earn nothing on this dataset.

One bug worth recording. The first version turned punctuation into spaces, so
`"M.G. Road"` became `m g road` while `"MG Rd"` became `mg road` - two spellings
of the same street that still did not match. Dotted initials are now glued
together *before* punctuation is stripped. The order of operations inside a
cleaning function matters as much as the rules.

### 3. Exact duplicate detection ([`src/matching.py`](src/matching.py))

Two kinds, both found by `groupby` rather than by comparison:

- **Exact** - the raw rows are identical. 13 pairs.
- **Normalized** - the raw rows differ but the cleaned rows are identical.
  18 more pairs, a 1.4x gain from preprocessing alone.

31 pairs, zero false positives, and only 29% of the answer. Grouping uses a hash
table so it costs about O(n), but hashing only finds *identical* keys -
`"ravi kumar"` and `"ravi k"` land in different buckets and can never be found
this way. That limitation is what the rest of the pipeline is for.

### 4. Blocking

```
n(n-1)/2  ->  445 records = 98,790 pairs
```

The work grows with n² while the number of real duplicates only grows with n.
Each record is filed under several cheap keys, and only records sharing a key
are compared:

1. `name token prefix + city` - one key **per token**, so a word swap or a typo
   in one token does not lose the record
2. `normalized phone`
3. `email user part` (dots and `+tags` removed)
4. `pincode + first letter of name` - a fallback when phone and email are both
   missing

A pair is a candidate if it shares **at least one** key.

```
98,790 possible pairs  ->  1,107 candidates   (98.88% skipped)
108 true pairs         ->  108 survive        (100% pair completeness)
```

Pair completeness is the number that matters. A true pair dropped here can never
be recovered downstream, so blocking sets a hard ceiling on final recall. The
union of keys is what makes it safe - each key alone is cheaper and worse:

| keys used | candidates | pair completeness |
|---|---|---|
| name_city | 865 | 99.1% |
| phone | 84 | 77.8% |
| email | 115 | 75.9% |
| pin_name | 350 | 64.8% |
| **all four** | **1,107** | **100.0%** |

### 5. Similarity ([`src/similarity.py`](src/similarity.py))

Three methods, because they fail in different ways.

**Fuzzy (RapidFuzz)** - character level, counts the edits needed to turn one
string into the other. Good at typos. We take `max(ratio, token_sort_ratio)`
because each fails where the other works:

```
"ravi kumar" vs "kumar ravi"   ratio 0.45   token_sort 1.00   (word swap)
"ravi kumar" vs "arvi kumar"   ratio 0.90   token_sort 0.50   (typo)
```

Using only `token_sort_ratio` - the first version - scored a simple typo lower
than two unrelated names, because sorting misaligns the words.

**Jaccard** - token level, order blind:

```
"12 mg road hyderabad"  ->  {12, mg, road, hyderabad}
"12 mg rd hyderabad"    ->  {12, mg, rd, hyderabad}

intersection = {12, mg, hyderabad}            = 3
union        = {12, mg, road, rd, hyderabad}  = 5
Jaccard      = 3 / 5 = 0.6
```

It survives reordering completely, but is blind to spelling - `road` and `rd`
are simply different words, which is why normalization expands abbreviations
first.

**TF-IDF + cosine (scikit-learn)** - Jaccard treats every word as equally
important, and it should not. `road` appears in hundreds of addresses; two
records both containing it tells us almost nothing. `kondapur` appears in a
handful, so sharing it is real evidence.

```
TF(word, record) = how often the word appears in this record
IDF(word)        = log(total records / records containing the word)
```

A word in every record gets IDF 0. Each record becomes a vector of weighted word
scores, and cosine similarity measures the **angle** between two vectors, so a
long address and a short one can still match - only direction matters. Measured
IDF on this dataset: `road` 1.80, `street` 2.32, `nagar` 2.49, against 6.43 for
a rare house number.

We compute cosine only for the 1,107 candidate pairs, not as a full 445×445
matrix. Because `TfidfVectorizer` L2-normalizes each row, cosine collapses to a
plain dot product.

### 6. Feature engineering

Eleven numeric features per pair, collapsed into five weighted components.

| feature | strength | why |
|---|---|---|
| `phone_match` | strong | ~395 distinct values; accidental agreement is very unlikely |
| `email_match` | strong | ~379 distinct values |
| `name_similarity` | medium | names genuinely repeat between different people |
| `address_similarity` | medium | families share addresses; `12 MG Road` vs `98 MG Road` scores 0.89 |
| `city_match` | weak | 7 possible values - unrelated records agree 1 time in 7 |

Phone is compared **exactly only**. A fuzzy phone score would be actively
harmful: `9876543210` and `9876543211` are 90% similar as strings and belong to
two different people.

### 7. Scoring and classification

```python
DEFAULT_WEIGHTS = {"name": 0.25, "email": 0.25, "phone": 0.25,
                   "address": 0.15, "city": 0.10}
```

These are a design choice, not a law of nature. They encode the table above:
identifier-like fields get more weight than categorical ones. The dashboard
exposes them as sliders.

Missing values are handled by **renormalisation**, not by scoring zero:

```
score = sum(w_i * f_i) / sum(w_i)      over available fields only
```

A pair with no email on either side is scored on name/phone/address/city, whose
weights sum to 0.75, and divided by 0.75 rather than 1.00. A blank is *no
evidence*, not *evidence against*.

```
>= 0.90        High Confidence Duplicate
0.75 - 0.89    Possible Duplicate  (send to a human)
<  0.75        Probably Unique
```

A similarity score and a classification are different things. The score is
evidence; the classification is an action. Where the cut-offs go depends on what
a mistake costs, not on the data - and merging two real customers is usually
worse than missing a duplicate, so the upper threshold is set high and the band
underneath goes to review rather than being decided automatically.

## Results

At the default threshold of 0.90, on 445 records:

```
                  Predicted: duplicate   Predicted: different
Truth: duplicate                    93                     15
Truth: different                     1                    998

Precision  0.989      Recall  0.861      F1  0.921
```

### Threshold experiment

```
 threshold  TP  FP  FN  precision  recall     f1
      0.70 106  17   2     0.8618  0.9815 0.9177
      0.75 103   5   5     0.9537  0.9537 0.9537
      0.80  97   2  11     0.9798  0.8981 0.9372
      0.85  96   2  12     0.9796  0.8889 0.9320
      0.90  93   1  15     0.9894  0.8611 0.9208
      0.95  87   0  21     1.0000  0.8056 0.8923
```

Raising the threshold demands more evidence, so fewer pairs clear the bar:
precision climbs from 0.86 to 1.00 while recall falls from 0.98 to 0.81. Best F1
is **0.954 at threshold 0.75**. There is no universally correct setting - 0.95
would be right for a system that merges automatically, 0.75 for one that only
builds a review queue.

Accuracy at 0.90 is 0.986 and it is **misleading**: flagging nothing at all would
still score 0.902, because almost every candidate pair really is a non-duplicate.
Precision and recall ignore the true-negative count, which is why they are the
right metrics for an imbalanced problem.

### Error analysis

The single false positive:

```
R0035  Aarti R      (no phone)               81 LAKE VIEW ROAD KORAMANGALA  Banglore
R0214  Aarti Reddy  aarti.reddy320@...  7798524013  81 Lake View Road Koramangala  Bengaluru
```

Two different people at the same address - siblings, from the confusable set.
The phone number would have disproved it, and the phone number is missing. Only
4 of 5 fields could be compared, the remaining weights were renormalised, and
the pair scored 0.93. This is the cost of the renormalisation rule: it is right
in general, but when the *one* field that would have said no is the missing one,
the score has no way to express that it rests on less evidence.

A representative false negative:

```
R0119  same name, same email, same address, DIFFERENT phone   ->  0.750
```

Someone changed their number. `phone_match = 0` costs a full 0.25 and drags an
otherwise perfect match to exactly the review boundary. Arguably correct
behaviour - a conflicting identifier really is evidence against - but it is the
main reason recall is 0.86 rather than higher.

## Limitations

- **Synthetic data.** Real records are messier and the error distribution here
  is whatever `make_dataset.py` produces. The scores should be read as "this
  method works on realistic variation", not as a benchmark.
- **The city dictionary is hand-built.** `CITY_SYNONYMS` maps 28 known spellings
  to 7 cities. A spelling nobody anticipated is not recognised. This does not
  generalise to a national dataset with thousands of cities.
- **Weights are hand-set, not learned.** Deliberate - a hand-set weight can be
  explained and defended, and fitting weights on 445 self-generated rows would
  mostly be learning the generator.
- **Blocking assumes city agreement for the name key.** Keys 2 and 3 cover a
  person who moved, but only if their phone or email survived.
- **`max(ratio, token_sort_ratio)` can only push scores up**, so it slightly
  increases false positives. The thresholds absorb this.
- **Missing values weaken the score silently.** The pair is scored on fewer
  fields but the number does not say so. `fields_compared` is reported next to
  every score, but it does not feed into the decision.
- **Pairwise only.** If A matches B and B matches C, nothing links A to C. Real
  systems cluster with a union-find or connected-components pass.
- **In-memory.** Everything is a pandas DataFrame. Fine at 445 records, and the
  blocking step is what would let it grow, but there is no chunking or database.

## Future Improvements

- Learn the weights with logistic regression on the ground truth and compare
  against the hand-set ones. This is the natural next step and would turn the
  project from a rule-based system into a supervised one.
- Cluster pairs into entity groups (connected components) instead of reporting
  pairs, so three records of one person become one cluster rather than three
  pairs.
- Add phonetic matching (Soundex / Metaphone) for names that sound alike but are
  spelled differently.
- Treat "conflicting identifier" as its own signal rather than just a zero, so
  that a deliberate mismatch and a missing value are scored differently.
- Sorted neighbourhood blocking as an alternative to key-based blocking, and
  compare pair completeness against the current scheme.

## How to run

```bash
pip install -r requirements.txt

python data/make_dataset.py      # regenerate the dataset (optional)

python -m src.preprocessing      # inspection + normalization report
python -m src.matching           # exact duplicates, blocking, scoring
python -m src.similarity         # side-by-side comparison of the 3 methods
python -m src.evaluation         # metrics, threshold sweep, error analysis

streamlit run app.py             # the dashboard
```

Every `src/` module runs standalone and prints its own stage. The dashboard
shows the same numbers - it calls the same functions, so nothing in it can drift
away from what the command line reports.
